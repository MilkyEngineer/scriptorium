# S5 — Two containers + SQLite WAL on the target filesystem; host snapshots

**Status:** passed 2026-10-18. Steps 1 and 3 passed on 2026-10-17; step 2 (24 h soak) ran 2026-10-17 12:37 UTC to 2026-10-18 12:37 UTC and passed. **Environment:** the operator's Docker host, `/data` on a dedicated **btrfs** subvolume on an NVMe pool; the same directory is also reachable through a FUSE union mount, which gave the refusal test a real target. Code: `users/fs.py`, `backup/snapshots.py`, `tests/soak/sqlite_soak.py`, `docker/host-snapshots/`.

## Step 1 — refusal of unsafe filesystems

`require_local_data_dir` run in a `python:3.12-slim` container with the module bind-mounted:

| Mount | Result |
| --- | --- |
| the data directory through the host's FUSE union path | refused: `fuse.<subtype>` named, message says what to mount instead |
| the same directory through its direct btrfs path | `fstype='btrfs', is_local=True, writable=True, wal_ok=True, locks_ok=True, problems=[]` |

Design points settled while implementing: the type comes from `/proc/self/mountinfo` (longest mount-point prefix), not `statfs`, because `statfs` cannot distinguish FUSE subtypes; the check is default-deny with an allowlist (ext4, xfs, btrfs, zfs, f2fs, bcachefs); `fuseblk`, `virtiofs`, `overlay` and `tmpfs` are refused; three functional probes (write+fsync, cross-process `flock`/`lockf`, WAL round-trip between two connections) run on every start. Architecture §6 updated.

## Step 2 — 24 h soak (passed 2026-10-18)

Two `python:3.12-slim` containers (`--read-only`, non-root, same uid as the data directory) share `/data/soak`: the writer commits one short `BEGIN IMMEDIATE` transaction per second touching one of 500 documents and up to 20 pages; the reader reads every 250 ms, enqueues jobs, and runs `PRAGMA integrity_check` plus a passive checkpoint hourly. Pragmas: WAL, `synchronous=NORMAL`, `busy_timeout=5000`, `foreign_keys=ON`. Pass rule: zero `SQLITE_BUSY`/`SQLITE_LOCKED`, zero other errors, every integrity check `ok`.

**Result (from the two JSON summaries; SQLite 3.46.1, Python 3.12.15, btrfs):**

The two maxima (about half a second, once each in 1.6 million transactions) are well inside the 5 s `busy_timeout` and never surfaced as an error. Both containers exited 0.

## Step 3 — host snapshot, read-only mount, index read

- Unprivileged `btrfs subvolume snapshot -r` works on the subvolume; **deleting** a subvolume needs root (no `user_subvol_rm_allowed`). Decision: a root cron on the host creates and prunes (`docker/host-snapshots/snapshot-btrfs.sh`, hourly, 24h/14d/8w retention, `MAX_DELETE` breaker); the container only reads a read-only bind mount of a **sibling** directory.
- The operator installed the script and cron and took one snapshot while the soak was writing (inode 256, not writable). Mounted at `/data/snapshots:ro` in a container: `list_snapshots` found it, `resolve_snapshot` rejected `../`, `<id>/../..` and unknown ids, a write probe failed with `EROFS`.
- The soak database inside the snapshot had a 4 MB `-wal`. `open_index_readonly` opened it with `mode=ro` (not `immutable=1`, which would silently drop WAL-only rows): `user_version` 1, 500 documents, 5 261 pages, 1 726 jobs, `integrity_check` = `ok`.
- The snapshot name format is `YYYY-MM-DDTHH-MM-SSZ`; Architecture §10.1 updated (it previously said `scriptorium-YYYYMMDDTHHMMZ`).

## Decisions

- `SNAPSHOT_STRATEGY=host` is the strategy for btrfs/ZFS hosts; `restic` remains for everything else.
- Pruning and creation are host-side root jobs; the container never writes to the snapshot directory.
- A nightly copy of the newest snapshot to a second filesystem is the "backup of the backup" (§13); it is an rsync from a read-only snapshot, never from the live directory.
