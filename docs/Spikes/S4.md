# S4 — Free-tier behaviour and the 50-day cut-off

**Status:** part (a) answered 2026-10-17; aged-document observation (b, c) pending 50 days.

## Question

Does the cloud API work at all on a free (non-Connect) account, and what does an aged (> 50 days unopened) document look like through the API?

## Evidence so far (read-only, S0's client, real account, no names recorded)

- `GET /sync/v4/root` returns a hash and a 16-digit generation; `GET /sync/v3/files/<hash>` returns the root index (schema 3 lines), each document index, and `.metadata`/`.content` blobs. HTTP 200 throughout for listing and metadata download.
- The library is two days old: 10 root entries (3 collections, 7 documents). No document has `lastOpened` older than two days, so step 2 cannot be observed yet.
- One document has `lastOpened` = `"0"` (epoch), i.e. never opened on the tablet after creation, and still has all its blobs. A never-opened document therefore cannot be told apart from an aged one by `lastOpened` alone; the heuristic must also consider `lastModified` and blob availability.
- A document already in the tablet's trash is still present in the root with `parent = "trash"` and downloadable blobs (confirms §7 trash handling: trash is a parent, not a deletion).
- Metadata keys seen: `createdTime`, `deleted`, `lastModified`, `lastOpened`, `lastOpenedPage`, `metadatamodified`, `modified`, `new`, `parent`, `pinned`, `source`, `synced`, `type`, `version`. `deleted` appears on some documents as `false` and is absent on others; treat absent as `false`.

## Plan for step 2 (aged document)

Create one scratch document in the scratch folder on the day S1 runs, record its UUID and the root generation locally (not in the repo), and do not open it on the tablet. Revisit after ≥ 50 days: is it still in the root, do its blobs download or 404, is anything flagged in `.metadata`, and does opening it on the tablet bring it back. Until then `deletion_cause` ships as `unknown` for documents that disappear from the root with no tablet-side trash or delete, per §7 step 4.

## (a) Operations without Connect

The operator's account has **no Connect subscription**. On it, the sync 1.5 API accepted everything S1 needed: root read, blob download, blob upload (`PUT /sync/v3/files/<hash>`), document index upload and generation-gated root commit, all HTTP 200, plus the expected 412 on a generation conflict. Uploaded documents appeared on the tablet after sync. Upstream's README claim that cloud mode needs Connect is therefore wrong for this account and firmware; G1 stands as written. What Connect changes (if anything) for the API, and the 50-day behaviour, remain to be observed.
