# S2 — Issuer + Claude OAuth end to end

**Status:** in progress (started 2026-10-17). **Issuer:** the reference Keycloak profile, `quay.io/keycloak/keycloak:26.4.7`, realm `docker/keycloak/realm-scriptorium.json`, behind the operator's TLS-terminating reverse proxy on another machine, with a CDN proxy in front. **Resource server:** Scriptorium's own `serve` with `SPIKE_TOOLS=true`.

## Step 1 — stack

- `start --import-realm` imported the realm on first start; `${SCRIPTORIUM_AUDIENCE}` and `${KC_HOSTNAME}` were substituted from the container environment (Keycloak replaces `${VAR}` in realm files at startup import; `${env.VAR}` is not the syntax).
- Public discovery (`/realms/scriptorium/.well-known/openid-configuration`) returns the configured issuer, PKCE `S256`, and advertises the registration endpoint (anonymous registration is off in the realm). RFC 8414 metadata at `/.well-known/oauth-authorization-server/realms/scriptorium` also answers 200. `client_id_metadata_document_supported` is absent: **CIMD needs Keycloak 26.6+**, so step 6 compares pre-registered clients with DCR only.
- Proxy deny rules verified from the internet: `/admin/`, `/admin/master/console/`, `/realms/master/`, `/realms/master/.well-known/openid-configuration` → 404.
- **Finding (step 7, partial):** `KC_HOSTNAME_ADMIN` is not an access control. On the proxy-facing port, `/admin/master/console/` and the master realm's discovery are served to any LAN client. The compose example therefore binds the admin console to a loopback-only second port (`127.0.0.1:8482`) and tells operators with a remote proxy to firewall the proxy-facing port to the proxy's address. Architecture §5.3 updated.
- `create-admin.sh` created the operator's realm user with a verified email and the `scriptorium-admin` role using the bootstrap admin; the temporary password was shown once and stored by the operator outside the repository.
- The resource server was not started until the adversarial review of the auth core had reported (no Critical or High findings; Mediums and Lows fixed first).

## Step 2 — claude.ai mobile web (passed 2026-10-17)

Custom connector with client ID `scriptorium-claude`, no secret. Login at the realm, first-login password change, then `spike_whoami` returned the operator's identity: `uid_hash` equal to `sha256(iss + "\n" + sub)` of the Keycloak user (checked independently), `is_admin: true` (the `realm_access.roles` mapping works end to end), scopes `email offline_access profile scriptorium`. Server side: one discovery + one JWKS fetch on the first authenticated call, then 200s; the log carries only the 12-character uid prefix. Observed flow on the phone: Claude opened the realm login page (client display name shown), first-login password change, then on submit the browser handed off straight to the Claude app via the `claude.ai` callback (treated as a universal link by the OS) while the browser tab stayed on the password-change page; no consent screen, as the clients are `consentRequired: false`. Nothing to fix on the issuer side. claude.ai web (2026-10-18) and Claude Desktop (2026-10-18) then used the same connector without any further login: the connector and its authorisation belong to the claude.ai account, not to the surface, so web, mobile and Desktop are one login and one Keycloak session. Claude Code is the separate client (step 3).

## Step 3 — Claude Code from outside the LAN (passed 2026-10-18)

`claude mcp add --transport http scriptorium <url> --client-id scriptorium-claude-code` on a machine on a foreign network, then `/mcp`. The browser landed on `http://localhost:<ephemeral port>/callback` (port 3118 this time) with `state`, `session_state`, `iss` (RFC 9207) and a single-use `code`; Keycloak's port-agnostic matching of the registered `http://localhost/callback` worked without any per-port registration. Login completed and the connector authenticated. Tool rendering in the terminal is recorded in S6. Note: because the same account was signed in to claude.ai on that machine, the claude.ai connector (`scriptorium-claude` session) also appeared in Claude Code as a second server; the two sessions are distinct in Keycloak and are the two surfaces for the step 5 refresh race.

## Step 6 (partial) — what happens without a pre-registered client

Adding the connector on claude.ai (mobile web) **without** an OAuth client ID: the client fetched the PRM, received the 401 challenge, discovered the issuer, then POSTed to the realm's dynamic registration endpoint twice. Keycloak's `Trusted Hosts` registration policy rejected both (`CLIENT_REGISTER_ERROR`, `error="not_allowed"`) and claude.ai reported "Couldn't register with ... sign-in service. You can try again, or add an OAuth Client ID". Result: with anonymous registration off, DCR fails closed and the pre-registered client ID is the only path, which is the intended posture (§5.3). The forwarded client address in the Keycloak event was the real remote address, so the proxy's `X-Forwarded-For` chain is honoured.
