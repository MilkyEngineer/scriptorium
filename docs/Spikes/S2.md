# S2 — Issuer + Claude OAuth end to end

**Status:** passed 2026-10-18 (steps 1–7; the session-revocation sub-step of 5 is the one item still to exercise, see below). **Issuer:** the reference Keycloak profile, `quay.io/keycloak/keycloak:26.4.7`, realm `docker/keycloak/realm-scriptorium.json`, behind the operator's TLS-terminating reverse proxy on another machine, with a CDN proxy in front. **Resource server:** Scriptorium's own `serve` with `SPIKE_TOOLS=true`.

## Step 1 — stack

- `start --import-realm` imported the realm on first start; `${SCRIPTORIUM_AUDIENCE}` and `${KC_HOSTNAME}` were substituted from the container environment (Keycloak replaces `${VAR}` in realm files at startup import; `${env.VAR}` is not the syntax).
- Public discovery (`/realms/scriptorium/.well-known/openid-configuration`) returns the configured issuer, PKCE `S256`, and advertises the registration endpoint (anonymous registration is off in the realm). RFC 8414 metadata at `/.well-known/oauth-authorization-server/realms/scriptorium` also answers 200. `client_id_metadata_document_supported` is absent: **CIMD needs Keycloak 26.6+**, so step 6 compares pre-registered clients with DCR only.
- Proxy deny rules verified from the internet: `/admin/`, `/admin/master/console/`, `/realms/master/`, `/realms/master/.well-known/openid-configuration` → 404.
- **Finding (step 7, partial):** `KC_HOSTNAME_ADMIN` is not an access control. On the proxy-facing port, `/admin/master/console/` and the master realm's discovery are served to any LAN client. The compose example therefore binds the admin console to a loopback-only second port (`127.0.0.1:8482`) and tells operators with a remote proxy to firewall the proxy-facing port to the proxy's address. Architecture §5.3 updated.
- `create-admin.sh` created the operator's realm user with a verified email and the `scriptorium-admin` role using the bootstrap admin; the temporary password was shown once and stored by the operator outside the repository.
- The resource server was not started until the adversarial review of the auth core had reported (no Critical or High findings; Mediums and Lows fixed first).

## Step 2 — claude.ai mobile web (passed 2026-10-17)

Custom connector with client ID `scriptorium-claude`, no secret. Login at the realm, first-login password change, then `spike_whoami` returned the operator's identity: `uid_hash` equal to `sha256(iss + "\n" + sub)` of the Keycloak user (checked independently), `is_admin: true` (the `realm_access.roles` mapping works end to end), scopes `email offline_access profile scriptorium`. Server side: one discovery + one JWKS fetch on the first authenticated call, then 200s; the log carries only the 12-character uid prefix. Observed flow on the phone: Claude opened the realm login page (client display name shown), first-login password change, then on submit the browser handed off straight to the Claude app via the `claude.ai` callback (treated as a universal link by the OS) while the browser tab stayed on the password-change page; no consent screen, as the clients are `consentRequired: false`. Nothing to fix on the issuer side. claude.ai web (2026-10-18) and Claude Desktop (2026-10-18) then used the same connector without any further login: the connector and its authorisation belong to the claude.ai account, not to the surface, so web, mobile and Desktop are one login and one Keycloak session. Claude Code is the separate client (step 3).

**Non-admin user (2026-10-18, found while running the allowlist check).** A second realm user with only the default roles was rejected by claude.ai ("Authorization with Scriptorium failed") and by Scriptorium with `401 missing_aud`, not the expected `403`: the access token had no `aud` and its `scope` lacked `scriptorium`. Cause: the export mapped `scriptorium-admin` as a role scope mapping on the `scriptorium` client scope, and Keycloak applies such a scope only to users holding one of its roles, so the admin was the only user who ever received the audience. Reproduced with a scripted code-flow login (claim names only, no token kept). Fix: the mapping moved to the two clients (`realm-scriptorium.json`, `move-admin-scope-mapping.sh` for existing realms). The step 2 result above was therefore admin-only until this fix. After the live fix the same user's token carried `aud` and `scope` including `scriptorium`, and `POST /mcp` answered `403` with the audit line `auth outcome=UserNotAllowed reason=not_on_allowlist` (no `WWW-Authenticate`, which is right: the token is valid, the user is not admitted). The test user was then deleted.

## Step 3 — Claude Code from outside the LAN (passed 2026-10-18)

`claude mcp add --transport http scriptorium <url> --client-id scriptorium-claude-code` on a machine on a foreign network, then `/mcp`. The browser landed on `http://localhost:<ephemeral port>/callback` (port 3118 this time) with `state`, `session_state`, `iss` (RFC 9207) and a single-use `code`; Keycloak's port-agnostic matching of the registered `http://localhost/callback` worked without any per-port registration. Login completed and the connector authenticated. Tool rendering in the terminal is recorded in S6. Note: because the same account was signed in to claude.ai on that machine, the claude.ai connector (`scriptorium-claude` session) also appeared in Claude Code as a second server; the two sessions are distinct in Keycloak and are the two surfaces for the step 5 refresh race.

## Step 6 (partial) — what happens without a pre-registered client

Adding the connector on claude.ai (mobile web) **without** an OAuth client ID: the client fetched the PRM, received the 401 challenge, discovered the issuer, then POSTed to the realm's dynamic registration endpoint twice. Keycloak's `Trusted Hosts` registration policy rejected both (`CLIENT_REGISTER_ERROR`, `error="not_allowed"`) and claude.ai reported "Couldn't register with ... sign-in service. You can try again, or add an OAuth Client ID". Result: with anonymous registration off, DCR fails closed and the pre-registered client ID is the only path, which is the intended posture (§5.3). The forwarded client address in the Keycloak event was the real remote address, so the proxy's `X-Forwarded-For` chain is honoured.

## Step 4 — token claims (passed 2026-10-18)

Decoded with a loopback PKCE code-flow script against the live realm (claim names only; no values were printed). Access tokens carry `acr, allowed-origins, aud, auth_time, azp, email, email_verified, exp, family_name, given_name, iat, iss, jti, name, preferred_username, realm_access, scope, sid, sub, typ`. `aud` is exactly the configured resource (`PUBLIC_URL`), `scope` is `openid email profile offline_access`, `realm_access.roles` holds `scriptorium-admin` for the admin user (the admin tools appear in that user's `tools/list` on Claude Desktop) and only `offline_access` for a non-admin; `email_verified` is present. The ID token carries no `realm_access` and its `aud` is the client, as it should.

**Finding, fixed:** the first realm export attached the `scriptorium-admin` role scope mapping to the `scriptorium` client scope. Keycloak applies a client scope that carries role scope mappings only to users who hold one of those roles, so a **non-admin's access token had no `aud` at all** and the server answered 401 `missing_aud`; the admin user never saw it. The mapping now sits on each client (`scopeMappings[].client`); `docker/keycloak/move-admin-scope-mapping.sh` migrates an imported realm in place, and `tests/docker/test_realm_json.py` guards the shape. After the fix a throwaway non-admin user (deleted afterwards) got a well-formed token and the server answered 403 `not_on_allowlist`, which is the M1 acceptance #1 deny path.

## Step 5 — lifetimes (passed 2026-10-18, revocation pending)

Realm configuration (`realm-scriptorium.json`): access token 15 min; SSO session idle 12 h, max 7 d; offline session idle 30 d, no offline max; refresh token rotation on (`revokeRefreshToken`, `refreshTokenMaxReuse` 1); both clients request `offline_access`, so connector sessions are offline sessions. Observed: the claude.ai connector linked on 2026-10-17 was still working on the evening of 2026-10-18 without a re-login across claude.ai web, mobile and Desktop (one connector, one Keycloak session), i.e. silent refresh survived well over a hundred access-token expiries and more than 24 h; Claude Code's loopback client has its own session and also stayed logged in across the day. Using claude.ai web and Desktop in the same hour did not log either out, which is the practical form of the two-surface refresh race under Max Reuse 1 (a stricter same-second race was not forced). **Still to do:** revoke the session in the admin console and confirm the client sees `invalid_grant` and re-prompts; this is a change to the live realm and waits for the operator's go-ahead.

## Step 6 — registration modes (decided: pre-registered clients ship)

| Mode | Status on Keycloak 26.4.7 | Observed / expected | Verdict |
| --- | --- | --- | --- |
| Pre-registered public clients + PKCE (`scriptorium-claude`, `scriptorium-claude-code`) | works | Steps 2–5 pass; one client per surface family; Claude Code's ephemeral loopback port matches the registered `http://localhost/callback` without per-port entries. | **ships** |
| Anonymous DCR | available, off (Trusted Hosts policy) | claude.ai tries it when no client ID is given and fails closed (above). Enabling it would mint one client per connection attempt per user with the realm's Max Clients policy (200) as the only bound, and each would need the audience scope attached by a registration policy. | not enabled; documented as an opt-in for operators who want zero-config connectors |
| CIMD (`client_id_metadata_document`) | not in 26.4.7 (`--features=cimd` lands in 26.6+) | not run | revisit when the pinned image moves |

## Step 7 — admin surface (passed 2026-10-18)

`KC_HOSTNAME_ADMIN` is not an access control (step 1 finding). The reference posture is: the proxy serves `/admin` and `/realms/master` to the operator's internal network only (404 elsewhere); the Keycloak container publishes the admin console on a second, loopback-only port as a tunnel fallback; a remote proxy's host firewalls the published ports to the proxy's address. Verified live: the console answers 200 at `KC_HOSTNAME_ADMIN` from the internal network and 404 through the public path, and `realm-scriptorium` discovery is public. One operator note: a browser that already holds a connection to the public path can keep showing the 404 until that connection closes.

## Decision

Pre-registered clients with PKCE, one per surface family, are the shipped mode (§5.3). Anonymous DCR stays off by default. The realm JSON, the migration script and the pinned Keycloak version are under `docker/keycloak/`.
