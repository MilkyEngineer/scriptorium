# S7 — Cloud change notifications as a poll trigger

**Status:** passed 2026-10-19 (run 2026-10-18 21:46Z to 2026-10-19 03:47Z with the development device tokens against the operator's account; read-only, no cloud writes). Listener landed the same day (`cloud/notifications.py`, `b276d6d`) and passed the live acceptance check on the deployed stack (§6 below). Evidence is scrubbed: no account, device or message identifiers, no document names.

## Question

Can the cloud's notifications websocket wake the sync loop so a change made on the tablet is readable within seconds rather than within `POLL_SECONDS`, and what does the channel look like in practice?

## Procedure

A probe script (session scratch, not committed) exchanged the dev device token for a user token exactly as `CloudClient` does, opened the websocket with that token, printed every message as a scrubbed shape (key paths, value types and lengths; literal values only for `event`, `eventType`, `eventVersion`), and after each message fetched the root pointer up to six times at 2 s intervals to measure when the new generation became readable. Six listener runs; the two long ones held a single connection for 2 h 05 m idle and then through 53 minutes of the operator taking meeting notes on the tablet.

## Evidence

### 1. Discovery and handshake

| Item | Observed |
| --- | --- |
| Old service-manager lookup (`service-manager-production-dot-remarkable-production.appspot.com/service/json/1/notifications`) | HTTP 404 with and without a token: dead, not used |
| Host | `<region>.tectonic.remarkable.com`, where `<region>` is the `tectonic` claim of the user token (a short region code). Path `/notifications/ws/json/1`. No device id or query string in the URL |
| Token | The **user token** (device token → user token, the same exchange sync uses), as `authorization: Bearer …`. The user token's claims include `auth0-profile` (name, email, nickname, picture-class fields), `device-desc`, `device-id`, `tectonic`, `scopes`, `exp` (3 h). The listener must read only `tectonic` and `exp` and never log claims |
| Browser-device token | Accepted. Both dev device tokens (registered as browser devices) connected |
| Response headers | `alt-svc`, `connection`, `date`, `sec-websocket-accept`, `upgrade`, `via` |
| Client pings | 20 s interval, always answered; no server-initiated pings seen |

### 2. Message shape

One JSON text frame per event, always the same shape (Pub/Sub relay):

```
message.attributes.auth0UserID   str len=30
message.attributes.event         'SyncComplete'
message.attributes.eventType     'SyncEventNotification'
message.attributes.eventVersion  '1'
message.attributes.googclient_traceparent  str len=55
message.attributes.orgID         ''
message.attributes.sourceDeviceID  str len=15
message.attributes.userID        str len=30
message.data                     null
message.messageid                digits len=17
```

30 events, 30 identical shapes. **No document UUID, no root generation, no change kind.** The channel is a pure wake-up: it says that some device finished a sync, nothing else. Only one source device was active (the tablet), so "own change versus another device" could not be distinguished; the listener does not need to, since it never acts on the payload.

### 3. Lag

| Measure | Result |
| --- | --- |
| Event → root generation readable | 30 of 30 events: the root pointer had **already moved on the first check**, 0.7–1.7 s after the frame (median 0.8 s, which is mostly the pointer fetch itself). No retry was ever needed |
| Tablet sync indicator → event | Not instrumented. The operator reported two deliberate syncs by chat; each produced one event inside the same minute. (An earlier sync produced nothing in the first probe run because that run still block-buffered stdout and was killed; a probe defect, not a missed notification) |

### 4. Disconnects, token lifetime, concurrency

| Behaviour | Observed |
| --- | --- |
| Idle | 2 h 05 m with no events: no server close, no ping failure |
| Token expiry | The server closed the socket **53 s before the user token's `exp`** (connection age 10704 s), with no close frame (`code=None`). A reconnect with the same token 40 s before expiry was accepted at the handshake and closed 12 s later; another was closed at the expiry second. The handshake with a fully expired token was not reached |
| Same token twice | A second connection with the same device's token **kicks the earlier one within about 2 s**, no close frame. Two probes with one token produced a kick ping-pong every 2–3 s until one was stopped (three separate occasions, all caused by stray probe processes) |
| Two device tokens, one account | Coexist. Each device gets its own slot and its own copy of every event |
| Server close frames | None in any of the ~25 closes: every drop is a bare TCP close |

### 5. Rate

| Period | Events |
| --- | --- |
| Idle, 22:22Z–00:27Z (2 h 05 m) | 0 |
| Meeting notes on the tablet, 00:27Z–01:20Z (53 min) | 29 |
| Gaps between those 29 events | min 5 s; 14 of 28 gaps ≤ 30 s; 18 ≤ 60 s; longest 748 s |

A writing session is a burst: the tablet syncs every few seconds to a couple of minutes while a page is being written. Polling on every event would mean a poll (and a committed version) every 5–30 s during a meeting.

### 6. Change kinds and the live listener (afternoon, 03:41Z–03:47Z)

With the listener deployed and `NOTIFICATIONS=true` on the live worker, the operator made metadata-only changes to one document on the tablet while the dev-token probe listened alongside. Both saw every frame; the worker's timings:

| Change | Frame → poll committed | Bytes committed |
| --- | --- | --- |
| Rename (after the tablet's network came back) | 4.1 s | 336 |
| Rename | 4.0 s | 338 |
| Rename | 4.1 s | 302 |
| Move to the root folder | 4.0 s | 338 |
| Move back into a folder | 4.0 s | 307 |
| Trash | 4.0 s | 302 |
| Restore, trash again, restore (four actions) | two frames, 4.1 s and 4.0 s | 307, 302 |

Each 4 s is the 2 s settle plus a 2 s poll. Renames, moves, trashing and restoring all produce the same `SyncComplete` frame; the tablet coalesces actions a few seconds apart into one sync (four actions became two frames), so the listener's own coalescing is in good company. A tablet with no network produces nothing until it reconnects, and then one frame for the backlog. The acceptance target "tablet edit visible within 30 s" passed with a 4 s result, and `NOTIFICATIONS` now defaults to `true`.

## Result

**Pass.** The websocket is reachable with the tokens Scriptorium already holds, accepts browser-device tokens, delivers an event for every sync within about a second of the root being readable, and stays up for the life of the user token. It carries no document information at all, so the wake-up-only design in Architecture §7 is not just preferred but the only one possible.

## Decision

The trigger is a wake-up and nothing more. `cloud/notifications.py` (`NotificationListener`, one per linked account, worker only; the server never connects):

1. **Connect:** renew the user token, derive the host from its `tectonic` claim (fall back to `eu`), open `wss://<host>/notifications/ws/json/1` with `authorization: Bearer`, client pings every 20 s. On every text frame call `AccountLoop.poke()`; log the `event` value only if it is in a small allowlist (`SyncComplete`), otherwise `other`. Never log or store `messageid`, `userID`, `auth0UserID`, `sourceDeviceID` or the trace header; never parse `data`.
2. **Poke timing:** `pause()` already starts the next poll at `last_poll_end + NOTIFY_MIN_GAP_SECONDS`, only after an `ok`/`partial` poll and never during backoff. Add a fixed settle of 2 s after the frame (root moved in ≤ 1.7 s in 30 of 30 cases), as a code constant, not a setting. `NOTIFY_MIN_GAP_SECONDS` stays at 10: with bursts of 5–30 s gaps that is at most a poll every 10 s during active writing, each committing one more version of the page being written (blobs are content-addressed, so the cost is the changed `.rm` file). Operators who prefer fewer versions raise the gap; the acceptance target "tablet edit visible within 30 s" holds for any gap ≤ 25 s.
3. **Token lifetime:** reconnect **proactively at `exp − 120 s`** (before the server's own cut at about `exp − 60 s`) with a freshly renewed token. Poke once after every successful (re)connect, because a notification during the handshake gap is lost, and the min-gap rule makes this free.
4. **One socket per device token:** the worker is the only listener and holds exactly one connection per account. A kick (connection closed within a few seconds of opening, repeatedly) means another process holds the slot, which happens during an overlapping worker restart: back off from 1 s doubling to 60 s with jitter, log `notifications_contended` once, keep trying. Never run a second listener for the same device token (tests use a fake server).
5. **Fallback:** every other failure (handshake rejected, network error, close) reconnects with exponential backoff 1 s → 300 s with jitter; after the first failure log `notifications_degraded` once and `notifications_restored` when a connection lasts ≥ 60 s. Polling at `POLL_SECONDS` continues unchanged throughout; the two-listings rule, the breaker and the budgets are the poll's own. A token rejection (401/403 on renewal) is the §7 "token rejected" class and is left to the poll loop; the listener stops for that account until the loop recovers.
6. **Settings:** `NOTIFICATIONS` becomes available (the `spike_s7_pending` refusal is lifted) and defaults to **`true`** since the live acceptance check passed (§6 above): the channel is read-only, costs one idle connection per account, and degrades to plain polling. `NOTIFY_MIN_GAP_SECONDS` default 10, range 1–3600, unchanged.
7. **Dependency:** `websockets` 17.2, licence `BSD-3-Clause` (wheel `License-Expression`, checked 2026-10-19). Record in Architecture §4.4.

## Follow-ups

- Observed in §6: renames, moves, trashing and restoring each produce a `SyncComplete` frame. Still unobserved: events for a desktop-app sync; whether Scriptorium's own pushes (the worker's cloud writes, M3) produce an event for the worker's own device (harmless if so: it costs one poll under the min-gap rule); the handshake response for a fully expired token (expected 401; the listener renews before connecting, so it should never send one).
- Whether a connection with a *new* user token for the *same* device kicks a socket opened with the previous token. The design assumes the slot is per device and reconnects sequentially (close, then open), so the answer does not change the implementation.
